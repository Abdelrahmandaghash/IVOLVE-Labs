Lab 4 · Docker Image Optimization and Export/Load

Build a Spring Boot app the "provided" way, watch it bloat, then rebuild it with a multi-stage Dockerfile that runs as a non-root user — and finish by learning to move an image between machines as a TAR file.

Theory — why images get big, and how multi-stage builds fix it

The app we're containerizing, ImageOptimization-, is a tiny Spring Boot service with one endpoint that returns "Hello from Dockerized Spring Boot!" on port 8080. Its final artifact is a single JAR file of a few megabytes. So why is the naive image ~800 MB?

The provided Dockerfile uses maven:3.9.15-eclipse-temurin-17-alpine as its only stage. That base image contains a full JDK and Maven — roughly 500–700 MB — and after mvn package the image also carries your source code, the target/ build directory, and the entire Maven dependency cache. All of that ships to production even though the app at runtime needs nothing but a JRE and the JAR.

🧠 Concept: multi-stage build
A multi-stage Dockerfile has two or more FROM instructions. Stage 1 (AS build) does the heavy compiling with Maven; stage 2 starts fresh from a slim JRE image and copies only the finished JAR over with COPY --from=build. Everything from stage 1 — JDK, Maven, source, caches — is discarded. Result: same app, a fraction of the size, plus a smaller attack surface.
🧠 Concept: run as non-root
Containers that run as root inside are a security risk: if an attacker exploits the app, they have root in the container. Creating a dedicated user (app) and switching to it with USER app means the process can only touch what that user is allowed to touch — standard practice for production images.

Part 2 · Build and run the optimized multi-stage image

6Study the optimized Dockerfile

This is Dockerfile.optimized from your repo (place it in Docker/Lab4/, i.e. one level above the cloned app). Every line explained:

# ---------- STAGE 1: the build environment (thrown away later) ----------
FROM maven:3.9.15-eclipse-temurin-17-alpine AS build

WORKDIR /app                       # sets the working dir; later COPYs land here
COPY pom.xml .                     # copy only the manifest first — layer caching!
COPY src ./src                     # then the source tree
RUN mvn -B package                 # -B = batch mode (no interactive prompts);
                                   # runs unit tests and produces target/*.jar

# ---------- STAGE 2: the runtime image that actually ships ----------
FROM eclipse-temurin:17-jre-alpine # JRE only, no Maven, no source. ~180MB base.

WORKDIR /app
RUN addgroup -S app && adduser -S -G app app
                                   # Alpine syntax: -S = system account;
                                   # creates group+user "app" (non-root)
COPY --from=build --chown=app:app /app/target/demo-0.0.1-SNAPSHOT.jar app.jar
                                   # pulls ONLY the JAR out of stage 1;
                                   # --chown makes the app user the file owner
USER app                           # every process now runs as "app", not root

EXPOSE 8080                        # documentation: the app listens on 8080
ENTRYPOINT ["java", "-jar", "app.jar"]  # the command that starts the app
💡 Why COPY pom.xml before src?
Docker caches each layer. If you change Java code but not dependencies, the RUN mvn layer would normally re-run and re-download every dependency. Copying pom.xml alone and running dependency resolution in an early layer means a source-only change skips the slow download step.
⚠️ The JAR name must match your pom
This app's pom.xml produces demo-0.0.1-SNAPSHOT.jar. If you reuse this Dockerfile for another Maven project, check target/ after a build and adjust the COPY --from=build line (or use a wildcard: /app/target/*.jar with exactly one JAR present).

7Build image2

Build from inside the cloned app directory so that pom.xml and src/ are in the build context, but point at the optimized Dockerfile that lives one directory up:

  • -f ../Dockerfile.optimized — use that file as the Dockerfile instead of ./Dockerfile.
  • -t image2 — name this build image2.
  • . — context is still the app directory (its contents are what COPY pom.xml and COPY src can see).

Watch the build: stage 1 runs Maven, then stage 2 starts a completely fresh Alpine JRE image and copies just the JAR. You should see the build finish with naming to docker.io/library/image2:latest.

Part 3 · Save, remove, and reload the image (portability)

🧠 Concept: docker save vs docker export
docker save writes an image — all its layers plus metadata — to a TAR archive. Because layers are preserved, you can docker load it on another Docker host (air-gapped server, colleague's laptop) and keep sharing layers between images. docker export is different: it flattens a container's filesystem and loses layer history — not what this lab wants.

11Save image2 to a TAR file

# run from Docker/Lab4/ (one level above the app) so the tar lands there
cd ..
docker save -o lab-image.tar image2
  • -o lab-image.tar — write the archive to this file. (Newer syntax: docker save image2 > lab-image.tar — same result.)
  • Check it: ls -lh lab-image.tar — it's roughly the size of the image (a few hundred MB).

12Delete image2 locally

docker image rm image2
docker image ls image2   # should return nothing now

This simulates the image being gone from the Docker host — e.g. a fresh machine with only the TAR file transferred over.

13Load it back and verify identity

docker load -i lab-image.tar
docker image ls image2
docker image inspect image2 --format '{{.Id}}'
  • docker load -i — reads the TAR and recreates the image with all original layers and metadata.
Expected output
Loaded image: docker.io/library/image2:latest

REPOSITORY   TAG       IMAGE ID       CREATED         SIZE
image2       latest    b71d04e9aa33   5 minutes ago   232MB

sha256:b71d04e9aa33c5f2...    <- identical to the ID from step 9
✅ The key insight
The image ID is byte-for-byte identical to the one before deletion. save → load is lossless; you can ship images to machines with no internet access and they'll be exactly the same build.

14(Optional) Run the loaded image once more

docker run -d --name container2b -p 8080:8080 image2
curl http://localhost:8080
docker rm -f container2b

Confirms the restored image is fully runnable, not just present in the list.

15Lab 4 cleanup

docker image rm image1 image2
rm lab-image.tar
# optional: remove the cloned app too
cd .. && rm -rf ImageOptimization-

Lab 5 · Docker Image Vulnerability Scanning with Trivy

Scan a Node.js image for known CVEs, produce an HTML report, then patch the base image and dependencies and prove the remediation worked with a rescan.

Theory — what Trivy looks for

Every Docker image contains two kinds of software, and both can carry known vulnerabilities:

  • OS packages — libraries baked into the base image (glibc, OpenSSL, zlib…). Fixed only by changing the base image to a newer build.
  • Language dependencies — npm/pip/maven packages (e.g. Express). Fixed by upgrading the dependency in your lock file.

Trivy (by Aqua Security) cross-references everything in an image against vulnerability databases (NVD + distro-specific trackers) and reports findings with a severity: LOW → MEDIUM → HIGH → CRITICAL, each with a CVE ID and, when a patch exists, the fixed version.

🧠 Concept: CVE vs. fix availability
A CVE means "this version is vulnerable". But not every CVE has a fix yet — sometimes the upstream package hasn't released one. Honest remediation means: fix everything that has a fix, and document what remains because no fix exists. Never claim "zero vulnerabilities" when the scanner still reports findings without available patches.

The demo app — TrivyImage — is deliberately insecure: node:18-bullseye (an old Debian base) + pinned express@4.18.2 (old, with known advisories). It serves / ("Welcome to the Trivy Security Lab!") and /health (JSON {"status":"UP"}) on port 3000.

Part 1 · Clone and build the initial image

cd Docker/Lab5

Part 2 · Install and verify Trivy

3Add Aqua's apt repository and install

This installs Trivy from Aqua Security's official Ubuntu/Debian package repo. Line by line:

# refresh package lists and pull the tools we need to add a repo securely
sudo apt-get update
sudo apt-get install -y wget apt-transport-https gnupg

# download Aqua's signing key, "dearmor" it from ASCII to binary format,
# and store it where apt trusts keys
wget -qO - https://aquasecurity.github.io/trivy-repo/deb/public.key \
  | gpg --dearmor \
  | sudo tee /usr/share/keyrings/trivy.gpg >/dev/null

# register the repo, pinned to your Ubuntu codename (e.g. "noble")
echo "deb [signed-by=/usr/share/keyrings/trivy.gpg] https://aquasecurity.github.io/trivy-repo/deb $(. /etc/os-release && echo "$VERSION_CODENAME") main" \
  | sudo tee /etc/apt/sources.list.d/trivy.list

sudo apt-get update
sudo apt-get install -y trivy

# verify — this also triggers the first vulnerability-DB download
trivy --version
Expected output
Version: 0.6x.x
Vulnerability DB:
  Version: 2
  UpdatedAt: 2026-10-20T12:00:00.000Z
  SchemaVersion: 2

If apt gives you trouble (proxy, permissions), Trivy's docs also offer a one-line installer that drops a static binary in /usr/local/bin:

Part 3 · Scan the image and generate an HTML report

4Full scan

trivy image trivy-lab:v1

The first run downloads the vulnerability database (tens of MB) and image layers — give it a minute. Output is grouped by target:

Expected output (shape)

└── ...

Exact findings change daily — Trivy's DB is updated continuously. Record what you see.

5Filter to HIGH + CRITICAL only

trivy image --severity HIGH,CRITICAL trivy-lab:v1

--severity filters the report. Teams usually gate CI on HIGH/CRITICAL because LOW/MEDIUM noise drowns out real risk. Notice how many entries say "Fixed in: …" — those are your remediation targets in Part 4.

6Generate an HTML report

Trivy's default output is a terminal table. For a shareable report, use Trivy's published HTML template:

# grab the official template once
curl -L https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/html.tpl -o html.tpl

# render the scan through that template into a standalone HTML file
trivy image --format template --template "@html.tpl" --output trivy-report-v1.html trivy-lab:v1
  • --format template --template "@html.tpl" — don't print the table; render results through the Go template in html.tpl (the @ means "read the template from this file").
  • --output trivy-report-v1.html — write to a file instead of stdout.

Open the report and review it (inside WSL, explorer.exe trivy-report-v1.html opens it in Windows browsers):

explorer.exe trivy-report-v1.html   # WSL → Windows interop opens your default browser
💡 What to extract from the report
For each HIGH/CRITICAL row note: package name (OS lib or npm package), installed version, fixed version (if any), and CVE ID. This table is your remediation checklist — it tells you exactly which base image and which npm dependency to bump in Part 4.
✅ Baseline recorded
Save trivy-report-v1.html and note the HIGH/CRITICAL count — you'll compare it with the v2 report after remediation.

Part 4 (Bonus) · Remediate: upgrade base image + dependencies

From the v1 report you saw two problems: an old Debian base (OS-package CVEs) and an old Express (npm CVEs). Fix both.

7Upgrade Express on the host

# still inside the cloned TrivyImage/ directory
npm install --save-exact express@latest
  • --save-exact — pin the exact version ("express": "5.1.0" style) instead of a ^ range — reproducible builds, no surprise minor-version jumps.
  • express@latest — newest published release, which contains fixes for the CVEs flagged in the report.
  • This also refreshes package-lock.json — the lock file the new Dockerfile will install from.
⚠️ Needs Node.js on your WSL host
This command runs on the host, not in Docker. Check with node --version. If you don't have it: sudo apt-get install -y nodejs npm, or use nvm. Express 5 also requires Node 18+.

8Study the remediated Dockerfile

This is Dockerfile.remediated from your repo — place it in Docker/Lab5/ and build from the cloned app directory:

FROM node:24-bookworm-slim   # NEW base: current Node LTS on Debian 12 slim —
                               # clears the OS-level CVEs and EOL Node 18

WORKDIR /app

COPY package*.json ./         # package.json + the refreshed package-lock.json
RUN npm ci --omit=dev         # "npm ci" = clean install STRICTLY from the lock file:
                               # faster, deterministic, no dependency drift.
                               # --omit=dev skips devDependencies → smaller image

COPY --chown=node:node app.js .   # app code owned by the non-root user
USER node                     # node images ship a built-in "node" user — use it

EXPOSE 3000
CMD ["npm", "start"]
🧠 Why npm ci instead of npm install?
npm install can resolve newer transitive versions than your lock file (drift = non-reproducible builds, and stale scans). npm ci installs exactly what the lock file says, deletes node_modules first, and fails loudly if the lock file is out of sync — the correct choice inside Dockerfiles.
💡 Where did the "node" user come from?
Official node images create a node user/group (uid 1000) out of the box. Unlike Lab 4 (where we created app on Alpine with adduser), here you just switch to it with USER node.

9Build the remediated image as ivolve-app:v2

# from inside TrivyImage/ — context needs package.json, package-lock.json, app.js
docker build -f ../Dockerfile.remediated -t ivolve-app:v2 .

-f ../Dockerfile.remediated points one directory up (where you placed the file); the trailing . keeps the app directory as the build context so the COPY lines find their files.

Lab 6 · Docker Environment Variables and Resource Management

Configure a Flask app three different ways (flags, env file, Dockerfile) and cap each container at 1 CPU / 256 MB — then watch Docker enforce the limits.

Theory — configuration outside the image

The demo app, PythonApp, is a Flask service that refuses to start without configuration:

APP_NAME = os.getenv("APP_NAME")
APP_ENV  = os.getenv("APP_ENV")

if not APP_NAME or not APP_ENV:
    raise ValueError("APP_NAME and APP_ENV environment variables are required")

It serves JSON on port 5000 showing which config it received. This is deliberate: it proves exactly where the variables came from. Same image, three configuration mechanisms — this is the core of the lab:

MethodHowTypical use
1 · -e flagsdocker run -e KEY=valueOne-off runs, CI scripts, tests
2 · --env-filedocker run --env-file env.txtMany variables, no shell history clutter
3 · Dockerfile ENVENV KEY=value baked inSensible defaults baked into the image
🧠 Precedence (later wins)
docker run -e overrides --env-file, which overrides a Dockerfile ENV default. So the standard pattern is: ENV provides defaults → env-file provides per-environment config → -e provides last-minute overrides. The three parts of this lab keep these isolated so you can see each one act alone.
🧠 Resource limits are cgroups, not suggestions
--cpus=1 and --memory=256m are enforced by the Linux kernel via cgroups. CPU is throttled (the process may only use 100% of one core's time); memory is hard — exceed it and the kernel's OOM killer terminates the container (exit code 137). Limits protect your host and your other containers from a runaway process.
💡 The numbers behind docker inspect

Lab 7 · Multi-Network Microservices, Volumes, and Bind Mounts

Build and connect a frontend, backend, and notification service across two isolated bridge networks, then persist logs and backend message data.

Theory — how services talk across networks

The demo app — MicroserviceApp — is three tiny Python services: the frontend (port 3000) receives your message from the browser and forwards it; the backend (port 5000) stores messages and calls the notifier; the notification (port 5001) logs that it got the message.

The core lesson: each Docker network has its own embedded DNS. A container name resolves to an IP only inside networks it's attached to — a service on a different network is unreachable by name, even though both containers run. That's the isolation this lab builds.

NetworkMembersWho can reach whom
frontend-backendfrontend, backendfrontend ↔ backend only
backend-notificationbackend, notificationbackend ↔ notification only
The frontend cannot reach the notification service directly — traffic must go through the backend. This is what «two isolated networks» means in production.
🧠 Concept: named volume vs bind mount
Named volume (e.g. backend-logs) lives in Docker's own area (/var/lib/docker/volumes/) — same behavior on every OS, reachable only from containers; right for service-internal data like logs. Bind mount (e.g. $(pwd)/backend-data:/app/data) maps a real path from your host into the container; you can read and edit it directly with cat or any editor — right when you want the data to outlive the containers.
┌─────────────┐ frontend-backend ┌─────────────┐ │ frontend │──────────────────────│ backend │ (backend = only member │ :3000 │ │ :5000 │ of BOTH networks) └─────────────┘ └──────┬──────┘ │ backend-notification ┌──────▼──────┐ │ notification│ │ :5001 │ └─────────────┘ frontend ──X──> notification (no shared network → unreachable) logs → named volumes: backend-logs, notification-logs data → bind mount: ./backend-data ↔ /app/data

Part 2 · Networks, volumes, and the host data directory

3Create the two bridge networks with separate subnets

docker network create --driver bridge --subnet 172.28.0.0/16 frontend-backend
docker network create --driver bridge --subnet 172.29.0.0/16 backend-notification
docker network ls
  • --driver bridge — Docker's default local network type (NAT'd so containers can also reach outside).
  • --subnet 172.28.0.0/16 reserves an IP range (65,536 addresses here); each network gets a different range so they never collide.
  • The names are fixed by the handout — they're what --network references below.
⚠️ If the subnet range already exists on your host
Some Docker hosts (especially behind a corporate VPN) already use 172.x ranges. If docker network create fails with Pool overlaps, pick two other unused CIDRs (e.g. 172.30.0.0/16 and 172.31.0.0/16) and continue — nothing later cares about the exact range as long as the two differ.

4Create the two named volumes for logs

docker volume create backend-logs
docker volume create notification-logs
docker volume ls

Each will hold a service's log file once mounted at /app/logs in Part 3 — the point is that the logs survive container removal.

5Create the host data directory (the bind mount)

# still inside MicroserviceApp/ — the path is used as-is by the bind mount below
mkdir -p backend-data
ls -ld backend-data

This folder maps to /app/data in the backend container and will hold messages.json — you can read your stored messages straight from the host with cat, no container needed.

💡 Why does -p "$(pwd)/…" need quotes?
$(pwd) expands to your current path; if it contains spaces (e.g. /mnt/d/My Projects/) the unquoted value would split into two arguments. Rule in bash: quotes must wrap the whole path:container-path pair but $(pwd) must still expand before Docker parses it — that's exactly what "$(pwd)/backend-data:/app/data" does.

Part 3 · Start notification and backend on their shared network

6Start the notification service first

We start notification before the backend so that when it resolves the name notification, the answer is already there.

docker run -d \
  --name notification \
  --network backend-notification \
  --network-alias notification \
  -v notification-logs:/app/logs \
  ivolve-notification:lab7
  • --network backend-notification — attach to this network only.
  • --network-alias notification — an extra DNS name inside the network (usually matches --name, but keeps the alias explicit).
  • -v notification-logs:/app/logs — mount the named volume from step 4 at the container's log folder.
  • -p is deliberately absent — nothing on the host needs this service; it only talks to the backend over the network.

7Run the backend with its notification URL and both mounts

docker run -d \
  --name backend \
  --network backend-notification \
  --network-alias backend \
  -e NOTIFICATION_URL=http://notification:5001/notify \
  -v backend-logs:/app/logs \
  -v "$(pwd)/backend-data:/app/data" \
  ivolve-backend:lab7
  • -e NOTIFICATION_URL=http://notification:5001/notify — the notifier addressed by name, resolved by that network's DNS. Writing localhost here would point at the wrong container.
  • -v backend-logs:/app/logs — backend logs into a named volume.
  • -v "$(pwd)/backend-data:/app/data" — the data bind mount: half on the host, half in the container.
  • --name backend / --network-alias backend — the name the frontend will use in Part 4.

8Attach the running backend to the second network too

# docker network connect = add a RUNNING container to another network
docker network connect --alias backend frontend-backend backend

# prove it: the backend now has two networks and two IPs
docker inspect --format '{{json .NetworkSettings.Networks}}' backend \
  | tr ',' '\n' | grep -E 'frontend-backend|backend-notification|IPAddress'
✅ Topology complete
The backend is now the only member of both networks — it reaches the notification on one side and the frontend on the other, while the frontend still cannot reach the notification at all: no shared network between them.
💡 Why the separate connect step?
docker run takes a single --network flag. Attaching at start time requires both --network flags in one run (supported), but the standard, explicit approach is docker network connect on a running container — which is what the handout uses.

Lab 8 · Containerized Node.js and MySQL Stack Using Docker Compose

Run the iVolve Node.js app and MySQL together with Docker Compose, keep database and application log data in volumes, verify connectivity, and publish the built app image to Docker Hub.

Theory — the mental shift Compose brings

In Labs 4–7 every service was its own docker run — you retyped networks, volumes, and flags each time, and tore the stack down by reversing commands by hand. Compose flips that: one docker-compose.yml declares the entire stack — you say what should be running, and Docker reconciles reality to match.

CommandWhat it does
docker compose configRenders the final config after merging .env substitutions — review before running
docker compose up --build -dBuilds missing images, starts all services detached
docker compose psLists the stack's services and their state (running, healthy…)
docker compose logs app dbLogs for both services — first place to look on failure
docker compose downStops and removes containers and network — volumes stay (your data survives)
docker compose down --volumesSame, plus removes the volumes — permanent data wipe
🧠 Concept: healthcheck + depends_on with condition
MySQL takes 10–30 seconds to become ready. If the app booted instantly it would hit ECONNREFUSED. depends_on: condition: service_healthy means «don't start the app until the db container reports healthy from its healthcheck». Here MySQL's healthcheck pings mysqladmin ping every 5s, up to 20 retries after a 20s grace period.
💡 $VAR vs $$VAR in Compose
Compose scans the file and substitutes ${VAR} from env (reading your .env). $$ means «literal $» — it reaches the container as $MYSQL_ROOT_PASSWORD for the shell inside to expand, not Compose. That's why the healthcheck reads p"$$MYSQL_ROOT_PASSWORD": Compose passes the line through, then the container's own sh expands it.

3Study docker-compose.yml line by line

This is the repo's supplied file (the copy in Docker/Lab8/) — annotated section by section:

services:                          # ← the map of services that form the stack
  app:                             #   service 1: the Node.js app
    image: ${DOCKERHUB_USERNAME:?Set DOCKERHUB_USERNAME in .env}/ivolve-app:lab8
                                   #   the tag it will be pushed under;
                                   #   ${VAR:?message} = fail with a clear error
                                   #   if VAR is missing from .env
    build:                          #   also BUILD it locally from:
      context: ./iVolveApp        #   the cloned repo (its files are the context)
      dockerfile: Dockerfile      #   that repo's own Dockerfile
    ports:
      - "3000:3000"              #   host 3000 → container 3000
    environment:                   #   runtime config for the app:
      DB_HOST: db                #   "db" = the OTHER service's name —
                                   #   Compose's internal DNS resolves it
      DB_USER: ${MYSQL_USER:?Set MYSQL_USER in .env}
      DB_PASSWORD: ${MYSQL_PASSWORD:?Set MYSQL_PASSWORD in .env}
      DB_NAME: ivolve             #   the required database name
    volumes:
      - app_logs:/app/logs       #   named volume app_logs mounted at /app/logs
    depends_on:
      db:
        condition: service_healthy #   start app ONLY after db is healthy
    networks:
      - ivolve-net               #   on the shared stack network

  db:                             #   service 2: MySQL
    image: mysql:8.4            #   official MySQL 8.4 LTS
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?Set MYSQL_ROOT_PASSWORD in .env}
      MYSQL_DATABASE: ivolve    #   MySQL's entrypoint CREATES this DB on first boot
      MYSQL_USER: ${MYSQL_USER:?Set MYSQL_USER in .env}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:?Set MYSQL_PASSWORD in .env}
    volumes:
      - db_data:/var/lib/mysql  #   named volume db_data = the data directory
                               #   (survives docker compose down)
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p\"$$MYSQL_ROOT_PASSWORD\" --silent"]
      interval: 5s             #   probe every 5 seconds
      timeout: 5s              #   give up on a probe after 5s
      retries: 20              #   20 failed probes → unhealthy
      start_period: 20s        #   grace period while MySQL initializes
    networks:
      - ivolve-net

networks:                         #   declared stack networks
  ivolve-net:
    name: ivolve-net          #   real name on the host (not project-prefixed)
    driver: bridge

volumes:                          #   declared named volumes (created by up)
  app_logs:
  db_data:
💡 Why is DB_HOST "db" and not localhost?
Each service has a DNS name on the Compose network. App and db share ivolve-net, so db resolves straight to the db container. localhost would look for MySQL inside the app container and fail.

  • sh -c '…' so the $MYSQL_USER variables are expanded inside the container from its environment — not by your host shell (where they'd expand empty).
  • MYSQL_DATABASE=ivolve in the container env is what made MySQL create the database on first boot.

Part 3 · Build and push the app image to Docker Hub

8Sign in and push

Compose already built and tagged the image <username>/ivolve-app:lab8 (from DOCKERHUB_USERNAME in .env). All that's left:

# opens a browser/device flow for auth — credential stays in your keychain
docker login

# push only the app service's image (not mysql)
docker compose push app
⚠️ Username case matters
Docker Hub usernames are lowercase only. With mixed case, the build succeeds but push fails with denied: … or repository does not exist. Fix DOCKERHUB_USERNAME to lowercase and rerun docker compose up -d --build.
💡 The image tag must match the repo path
Docker Hub requires the full username/image:tag. The file's image: ${DOCKERHUB_USERNAME:?…}/ivolve-app:lab8 guarantees it — without your username set, even up fails at config time.

9Confirm the image tag before sharing

docker image ls --filter 'reference=*/ivolve-app:lab8'
  • --filter 'reference=*/ivolve-app:lab8' — wildcard on the repo name, so it matches whatever your username is.
  • After a successful push the image lives in your Docker Hub account — any machine can now docker pull <username>/ivolve-app:lab8.

REPOSITORY                  TAG       IMAGE ID       CREATED        SIZE
yourname/ivolve-app         lab8      9c4d2e1f8a7b   5 minutes ago  150MB

Lab 8 cleanup

10Tear down, optionally keeping or wiping data

# stop + remove containers and the network — KEEP the volumes (db data + logs)
docker compose down

# if you also want to delete the persisted MySQL database and app logs:
docker compose down --volumes

💡 Which one should you run?
Plain docker compose down stops the stack but keeps your data — up brings it right back. --volumes is a permanent wipe of the database and logs — use it once your report is saved. Your pushed Docker Hub image remains in your account until you delete it on the website.
